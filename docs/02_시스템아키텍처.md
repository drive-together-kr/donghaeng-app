# 동행 시스템 아키텍처

> 설계 원칙: **"현대차그룹이 실제로 운영한다면"** 기준의 운영(Production) 아키텍처를 먼저 정의하고,
> 공모전 MVP는 **같은 구조를 축소한 형태**로 구현한다. MVP 코드는 서비스 경계(패키지)를 운영 구조와 똑같이 나눠서,
> 나중에 서비스 분리만 하면 되도록 만든다.

### 1.1 왜 이 구조인가

| 결정 | 이유 |
|---|---|
| **차량 ↔ 서버는 MQTT** | 커넥티드카 업계 표준 텔레매틱스 프로토콜. 이동 중 끊김·재연결에 강하고(세션 유지, QoS1 재전송), 메시지가 작고, 그룹 단위 팬아웃(토픽 구독)이 자연스럽다. HTTP 폴링 대비 지연·배터리·데이터 사용량이 작다. |
| **브로커 뒤에 Kafka** | 차량 수백만 대의 텔레메트리를 서비스별로 독립 소비(위치 갱신, 이벤트 판정, 분석)하고, 장애 시 재처리 가능. |
| **Redis에 실시간 상태** | "지금 그룹원이 어디 있는가"는 최신값만 필요 → 인메모리 + TTL. GEO 명령으로 거리 계산. |
| **PostgreSQL에 메타** | 사용자·차량·그룹은 관계형·트랜잭션 데이터. |
| **기기 페어링 = OAuth 2.0 Device Authorization Grant (RFC 8628)** | 차 화면에는 키보드 입력이 불편하다. TV·차량 로그인 표준 방식: 차가 코드를 띄우고 폰이 승인. Pleos App Market 로그인도 차→폰 로그인 흐름을 쓴다. |
| **그룹 초대 = 단기 서명 토큰 QR** | QR에 그룹 ID를 그대로 넣으면 유출 시 누구나 합류. 10분 유효 + 1회용(또는 최대 인원) 서명 토큰으로 발급. |
| **서비스는 Kotlin/Spring Boot** | 차량 앱과 같은 언어(Kotlin), 국내 대기업 백엔드 표준 스택, 모듈러 모놀리스 → MSA 분리 용이. |

### 1.2 신뢰 경계와 보안
- 차량: mTLS 인증서(운영) / MVP는 차량 JWT + TLS. 차량은 **자기 토픽에만 publish**, 자기가 속한 그룹 토픽만 subscribe (브로커 ACL).
- 폰(companion 모듈): 호스트 공식 앱의 OAuth2 토큰을 서버가 `ExternalTokenVerifier` 로 검증해 서비스 JWT 발급. 모듈은 MQTT 대신 REST + 푸시 사용(배터리·OS 제약).
- 서버만 그룹 토픽에 publish → 차량끼리 직접 메시지를 주고받지 않는다(위조·스팸 차단, 서버가 검증·정규화).
- 위치는 그룹 종료 즉시 삭제, Redis TTL 10분. 로그에 좌표·이름 마스킹.

### 1.3 규모 가정 (운영)
- Pleos 탑재 2,000만 대(2030 계획) 중 동시 그룹 주행 차량 0.5% = 10만 대
- 위치 1Hz × 10만 = 초당 10만 메시지(약 200B) ≈ 20MB/s → 브로커 클러스터 + Kafka 파티셔닝(키 = groupId)으로 수평 확장
- 그룹당 팬아웃은 최대 10대 수준이라 브로커 부하가 선형적

## 2. 공모전 MVP 아키텍처 (Build Now)

운영 구조를 **같은 경계로 축소**한다.

| 운영 | MVP |
|---|---|
| AWS IoT Core / EMQX 클러스터 | **EMQX 단일 노드** (Docker) |
| Kafka | 없음 — EMQX → 서버로 직접 (서버가 MQTT 공유 구독 `$share/server/...`) |
| 서비스 8개 (EKS) | **`donghaeng-server` 모듈러 모놀리스 1개** (Spring Boot, 패키지 = 운영 서비스 이름) |
| Aurora / ElastiCache | **PostgreSQL 16 + Redis 7** (Docker) |
| 공식 앱 계정 OAuth2 토큰 검증 | **dev 로그인(provider=dev)** — 서버에는 `ExternalTokenVerifier` 인터페이스만 두고 MVP 구현은 Dev. 차량 연결은 Device Authorization Grant(대체 수단) |
| mTLS | 차량 JWT로 MQTT 인증 (EMQX JWT auth 플러그인) |
| FCM | 호스트 앱 푸시(FCM) 또는 모듈 폴링(개발 초기) |

### 2.1 배포
- **로컬 개발:** `docker compose up` (emqx, postgres, redis, server) — 에뮬레이터에서 호스트는 `10.0.2.2`
- **데모·심사:** 클라우드 VM 1대(예: AWS Lightsail / Oracle Cloud 무료 티어 / GCP e2-small, 서울 리전)에 동일 compose + Caddy(HTTPS, 자동 인증서)
  - 공개 주소: 고정 도메인 없이 `https://<VM-IP>.sslip.io`(REST, Caddy 자동 인증서) / `ssl://<VM-IP>.sslip.io:8883`(MQTT). 서버 설정값 `DH_PUBLIC_BASE_URL`·`DH_MQTT_PUBLIC_URI`로 주입(03 문서)
- 시연 영상·PT에서 **"실제 서울 리전 서버를 거쳐 두 차가 연결"**되는 장면 + 지연 시간(ms) 표시

### 2.2 MVP 패키지 구조 (서버)
```
donghaeng-server/
 └─ src/main/kotlin/app/donghaeng/
     ├─ identity/     # 계정, 차량 페어링(device code), JWT
     ├─ group/        # 그룹·초대 토큰·멤버십
     ├─ presence/     # 실시간 상태 (Redis)
     ├─ event/        # 이벤트 정규화·팬아웃
     ├─ routesync/    # 선두 경로 → 멤버 제안
     ├─ insight/      # 휴게소 제안·이탈 감지 규칙
     ├─ poi/          # 휴게소 데이터
     ├─ notify/       # 음성 문구·푸시
     ├─ mqtt/         # MQTT 클라이언트(공유 구독), 토픽 라우팅
     └─ common/       # 에러, 시간, 직렬화
```
각 패키지는 다른 패키지의 내부 클래스를 직접 참조하지 않고 `*Api` 인터페이스로만 호출한다(→ 추후 서비스 분리).

## 5. 주요 시퀀스

필드명·응답 형태는 docs/03 가 기준(계약)이다. 여기서는 docs/03 의 이름을 그대로 쓰되 요약만 적는다.

### 5.1 차량 페어링 (Device Authorization Grant)
```
차량앱 → POST /v1/device/code {vehicleId, model, brand, appVersion}   → {deviceCode, userCode, verifyUri, expiresIn, interval}
차량앱: verifyUri(= {DH_PUBLIC_BASE_URL}/pair?c={userCode})를 그대로 QR 표시 + userCode 표시, interval마다 POST /v1/device/token {deviceCode} 폴링
호스트 앱(companion 모듈, 로그인 상태) → QR 스캔 → DongHaeng.pairVehicle(payload, nickname) → POST /v1/device/approve {userCode, nickname}   ※ 대체 수단(계정에 차량이 없을 때)
차량앱 폴링 → {vehicleAccessToken, refreshToken, vehicle: {vehicleId, nickname, ownerId}, mqtt: {uri, clientId, username}}   (docs/03 §1.2)
차량앱 → MQTT CONNECT (uri = mqtt.uri, password = vehicleAccessToken)
```

### 5.2 그룹 생성·QR 합류
```
차량A(방장) → POST /v1/groups {name, destination, maxMembers}   → {groupId, leaderVehicleId, invite: {token, url, expiresAt}, mqttTopics}   (docs/03 §2.1)
차량A: invite.url(= {DH_PUBLIC_BASE_URL}/j/{invite.token}) QR 표시, MQTT subscribe dh/v1/group/{groupId}/#
차량B 소유자의 공식 앱(companion 모듈) → 스캔 → DongHaeng.joinGroup → POST /v1/groups/join {inviteToken, vehicleId?}  (vehicleId 생략 시 대표 차량)
서버: 멤버십 추가 → MQTT publish dh/v1/vehicle/{vehicleB}/cmd {type: GROUP_JOINED, groupId, leader, destination}
차량B: subscribe 그룹 토픽, "선두차 목적지로 안내할까요?" → 수락 시 NaviHelper.requestRoute / requestRouteWithWaypoints
서버 → 그룹 토픽 publish {type: MEMBER_JOINED}
```

### 5.3 이동 중 텔레메트리·이벤트
```
차량 → dh/v1/vehicle/{vid}/telemetry  (1Hz 위치, 30s ETA)         QoS0
차량 → dh/v1/vehicle/{vid}/event      (LOW_FUEL, HARD_BRAKE, WAYPOINT_ARRIVED…) QoS1
서버(presence) Redis 갱신 → 2초마다 그룹 스냅샷 publish dh/v1/group/{gid}/state  QoS0
서버(event)   정규화·중복 제거 → dh/v1/group/{gid}/event        QoS1
서버(insight) 규칙 판정 → dh/v1/group/{gid}/event {type: REST_STOP_PROPOSAL}
차량들: 이벤트 수신 → 신선도 검사(5초 초과 시 음성 생략) → TTS 안내
        + 플로팅 패널 소식 줄(10초) 또는 (플로팅 창 권한이 없으면) 알림 카드(서버 시계 기준 60초 이내, 5초 표시, 회전 300 m 이내면 회전 후) — 내 차 이벤트는 생략
```

### 5.4 선두 경로 동기화
```
선두차 NaviHelper onDestinationChanged/onWaypointChanged → event {ROUTE_CHANGED, destination, waypoints}
서버(routesync) → 멤버 차량 cmd {type: ROUTE_FOLLOW_PROPOSAL, …}
멤버 차량: 음성 "선두차가 OO휴게소를 경유지로 추가했어요. 따라갈까요?" → 수락 → NaviHelper.addWaypoint
```

## 6. 지연·끊김 설계
- MQTT keepalive 30s, clean start = false, session expiry 1h → 터널 통과 후 QoS1 이벤트 재수신
- 모든 메시지에 `ts`(발생 시각, epoch ms)·`seq`. 수신 측은 `now - ts > 5s` 이벤트는 음성 생략·화면만 "N초 전" 표시
- 위치는 dead reckoning: 마지막 위치 + 방향 + 추정 속도로 최대 30초 외삽, 이후 "연결 끊김" 표시
- 측정: 이벤트 발생→타 차량 수신 지연을 앱 내 디버그 오버레이로 표시(시연용)
