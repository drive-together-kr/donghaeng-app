# 동행 테스트 · 데모 계획

## 1. 개발 환경
- Windows PC, Android Studio 2026.1.3, Pleos Connect Emulator v2.1.0 (API 34, x86_64, RAM 4GB, Cold boot)
- 에뮬레이터 2대(둘 다 Pleos 이미지): `Pleos_Connect_v2.1.0`(차 A, **pleos** flavor, 실 SDK) + `Pleos_B`(차 B, **fake** flavor — 같은 시스템 이미지의 복제 AVD, GPX 를 스스로 재생). 2026-10-27 확정, 그 전까지 차 B 역할이던 `Medium_Phone` AVD(API 37 Play 이미지, 과부하)는 삭제했다.
  - `Pleos_B` 만들기: `%USERPROFILE%\.android\avd\Pleos_Connect_v2.1.0.avd\config.ini` 를 `Pleos_B.avd\config.ini` 로 복사해 `AvdId=Pleos_B`, `avd.ini.displayname` 만 바꾸고 `Pleos_B.ini`(path 지정)를 만든다. RAM 은 이미지가 최소 4096 MB 를 강제한다. 실행: `emulator -avd Pleos_B -port 5558` → `emulator-5558`.
  - 두 AVD 공통 튜닝(2026-10-27, `config.ini.bak` 백업): `hw.gpu.mode=host`(실측 렌더러 NVIDIA RTX), `fastboot.forceColdBoot=no` + `fastboot.forceFastBoot=yes`(Quick Boot — 실행 인자에 `-no-snapshot-load` 를 주지 않는다), `hw.audioInput=no`(가상 마이크 DirectSoundCapture 실패 로그 제거). 부팅 약 20 s.
- Virtual Console(차 A 만 — 차 B 는 fake 차량 어댑터라 필요 없다): `adb -s emulator-5556 forward tcp:8089 tcp:8088` → http://127.0.0.1:8089 또는 `python tools/demo/vc.py --port 8089 soc 12`.
- 위치 이동: 차 A 는 `python tools/demo/replay_gpx.py --serial emulator-5556`(lead.gpx → `adb emu geo fix` 1 Hz → Android LocationManager 소스), 차 B 는 `FakeNaviAdapter` 가 follow.gpx 를 재생(합류 제안 수락 뒤 출발). Extended Controls 의 Routes 재생은 쓰지 않는다.
  - **차 A 는 시연 전에 위치 소스 순서를 바꾼다(2026-10-28):** Pleos AVD 의 순정 내비 위치는 기본값(성남 수정구)에 고정돼 있고(아래 §1.2), 동행 앱은 내비 위치를 먼저 쓰므로 그대로 두면 차 A 가 움직이지 않는다. `adb -s emulator-5556 shell am broadcast -n app.donghaeng.car/.debug.DemoControlReceiver --es action loc_order --es order android_first` → 앱 재시작 → 로그 `location: 소스 순서 android_first`, `telemetry … src=ANDROID`. 실차에서는 기본값(`default`)을 쓴다.
  - 순정 내비 화면의 '내 차' 아이콘은 에뮬레이터에서 움직이지 않는다(§1.2). 시연 영상에서 차의 움직임은 순정 내비 위 플로팅 패널의 간격·도착 시각·소식 줄과 음성으로 보이고(두 대 모두 플로팅 창 허용 = 패널 모드라 헤드업 카드는 뜨지 않는다 — 카드는 권한이 없는 '카드 + 음성' 모드에서만), 순정 내비는 경로·경유지(휴게소)·안내 카드를 보여 준다.
- **Pleos AVD 네트워크 주의:** Pleos_Connect_v2.1.0 은 Wi-Fi(wlan0)가 켜져 기본 네트워크가 되면 호스트(10.0.2.2)에 닿지 않는다(유선 eth0 으로만 닿음, 앱에는 `SocketTimeoutException`). 시연 전 `adb -s <pleos-serial> shell svc wifi disable` 로 Wi-Fi 를 끈다(되돌리기 `svc wifi enable`). 확인: `adb -s <serial> shell ping -c 1 10.0.2.2`.
- 서버: `infra/` 에서 `docker compose up -d` — 호스트 포트: 서버 8080, EMQX 1883/18083, Redis 6379, PostgreSQL **15432**(로컬 PostgreSQL 18이 5432 점유). 에뮬레이터에서 서버 주소 = `http://10.0.2.2:8080` (`DH_PUBLIC_BASE_URL=http://10.0.2.2:8080`)
- 클라우드 서버(T32, 2026-10-28~): **`https://3.24.206.147.sslip.io`** — AWS EC2 시드니(ap-southeast-2) c7i-flex.large, 탄력적 IP. MQTT 기본 `ssl://3.24.206.147.sslip.io:8883`, 8883 이 막힌 망은 `wss://3.24.206.147.sslip.io/mqtt`(443, 앱이 자동 전환). release APK 의 기본 서버가 이 주소다(`-PdhCloudHost=3.24.206.147.sslip.io`). 헬스체크 `bash infra/cloud/deploy.sh --check-only 3.24.206.147.sslip.io`(9종), 운영·비용 infra/cloud/README.md §9. 클라우드 dev 로그인은 접속 키 필요(`DH_DEV_LOGIN_KEY`, docs/10 R20)
- 폰(demo-host = 공식 앱을 흉내 낸 companion 호스트 앱): **USB 로 연결한 실기기**(같은 Wi-Fi) — 로컬 서버는 PC IP 로 접근(`DH_PUBLIC_BASE_URL=http://<PC-IP>:8080`, 방화벽 8080/1883 인바운드 허용 필요), 클라우드 배포 후엔 `https://<VM-IP>.sslip.io`. 폰이 없을 때는 `python tools/demo/api.py --email <dev 이메일> pair|rename|join|message` 로 같은 REST 를 대신 호출해 리허설한다.

### 1.2 순정 내비 위치 이동 시도 결과 (2026-10-28, Pleos_B AVD 실측)
| 방법 | 결과 | 근거 |
|---|---|---|
| (a) 순정 내비 자체 모의 주행 | 없음 | 내비 설정 전체(충전소·경로·사운드·버전·데이터 관리)와 경로 화면에 모의 주행 메뉴가 없다. NaviHelper 공개 API 에도 없다 |
| (b) LocationManager 테스트 제공자(`cmd location providers add-test-provider gps/fused` + `set-test-provider-location`) | 내비 위치 그대로 | 안드로이드 gps·fused 제공자와 Pleos FusedLocation 서비스는 새 좌표를 받았지만 내비 엔진의 위치(`mapmatching org`)는 바뀌지 않았다 |
| (c) 체크섬을 맞춘 NMEA 를 `adb emu geo nmea` 로 주입 | 내비 위치 그대로 | GNSS HAL 은 호스트(`geo fix`) 형식과 같은 필드 구성이어야 파싱하고, 프레임워크로 내보내는 NMEA 는 HAL 이 다시 만들며 체크섬을 항상 `*47` 로 고정한다(에뮬레이터 버그) → 내비 `NmeaParser` 가 모두 거부 |
| (c') 고도·속도·좌표 끝자리를 조절해 그 초의 문장 XOR 이 `0x47` 이 되게 한 `geo fix` | 문장은 통과, 위치는 그대로 | 20초 동안 내비가 거부한 문장 0건(파서 통과)이지만 엔진 위치는 바뀌지 않음. 위치 서비스 KPI 의 '측위에 쓰인 위성 수'가 0 이라(에뮬레이터가 보고하지 않음) 내비 엔진이 측위를 받아들이지 않는 것으로 보인다 |
| (d) Virtual Console 위치 기능 | 없음 | Virtual Console HTTP API·웹 UI 에 위치·GNSS 항목이 없다(차량 상태·기어·속도·HVAC 등만) |

결론: 이 에뮬레이터에서는 순정 내비의 내 차 아이콘을 GPX 경로대로 움직일 수 없다(docs/10 R17). 동행 쪽 위치는 차 A 를 `android_first` 로 두고 `replay_gpx.py` 로, 차 B 는 fake 내비 GPX 로 움직인다.
대신 증명은 순정 내비 위 **플로팅 패널의 간격 숫자**로 한다 — `docs/images/surfaces/impl_11_panel_gap_follows_gpx.gif`(차 A 를 400 km/h 로 재생, 차 B 와의 간격 2.1 → 2.4 → 3.4 km, 3 km 를 넘으면 주황, 중간에 급제동 카드 1장 — **카드 부분은 옛 동작**: 2026-10-28 지시 전 캡처라 패널 모드에서도 카드가 떴다. 지금은 같은 순간에 패널 소식 줄(빨강) + 음성만. 또 이 카드는 선두 A 가 받은 것이라 **수신 대상 규칙 이전 동작**이기도 하다 — 아래 §1.3 주). 차 A 앱을 새로 띄운 뒤 약 1분은 위치가 순정 내비 고정 위치로 내려갔다 올라올 수 있으니(docs/10 R17) 텔레메트리 `src=ANDROID` 를 확인하고 시작한다.

**TBT 게이트 확인(2026-10-28 — 재캡처 완료: 위 표 `impl_02_after…`·`impl_13`~`impl_16`, TBT 단위 = 미터 확인):** Pleos AVD 순정 내비는 위치가 고정돼 TBT 가 늘 같은 값이라(§1.2·docs/10 R17) 디버그 `tbt` 액션으로 다음 회전 거리를 덮어써 증명한다(`R=adb -s <serial> shell am broadcast -n app.donghaeng.car/.debug.DemoControlReceiver --es action`).
1. 패널 모드(impl_02 재캡처, **뒤차 B 에서** — 급제동은 출처보다 뒤차만 받는다): `$R event --es type HARD_BRAKE`(출처 기본값 = 스냅샷의 내 바로 앞 차) → 로그 `demo: event … card=SKIPPED mode=PANEL`(debug 빌드면 `surface: card skip HARD_BRAKE reason=panel-mode`), 패널 소식 줄(빨강) + `voice: speak HARD_BRAKE`, 순정 내비 TBT 위 헤드업 카드 없음 → 캡처.
2. 카드 + 음성 모드(`adb -s <serial> shell appops set --user 10 app.donghaeng.car SYSTEM_ALERT_WINDOW deny`, 끝나면 `allow` 로 되돌림 → `$R surface` 로 `mode=CARDS_ONLY` 확인): `$R tbt --ei m 120 --ei for_s 60` → `$R event --es type HARD_BRAKE --es source veh_DEMO2` → `surface: card deferred type=HARD_BRAKE tbt=120m kind=DEBUG why=near`, 카드 없음 → 캡처 → `$R tbt --ei m 280 --ei for_s 60` → 1초 뒤에도 카드 없음(다음 회전이 아직 300 m 안 — 연속 회전도 이렇게 계속 미룬다) → `$R tbt --ei m 800 --ei for_s 60` → 1초 안에 `surface: card released type=HARD_BRAKE reason=far tbt=800m/DEBUG` + 카드 5초 뒤 사라짐 → 캡처. `$R surface` 의 `cards=… held=0 deferred=1 released=1 lastTbt=…`.
   - **AVD 주의:** 차 A(pleos) 순정 내비가 경로 안내 중이면 TBT 가 고정값(예: `impl_03` 의 80 m)이라 덮어쓰기가 없을 때 '카드 + 음성' 모드의 카드는 모두 미뤄졌다가 120초 뒤 `surface: card expired …` 로 버려진다(고장 아님 — 위치가 안 움직여(docs/10 R17) 회전을 지나지 않는다 — TBT 고정값 주의는 R16). 카드 화면(`impl_05`·`impl_07`·`impl_08`, 장면 7 의 차 A 카드) 재캡처는 내비 안내를 끈 상태이거나 `$R tbt --ei m 800 --ei for_s 120` 덮어쓰기 중에 한다. 차 B(fake)는 GPX 진행에 따라 1.2 km 마다 가상 회전이 있어 회전 뒤에 카드가 나온다.
3. 모름 → 즉시: `$R tbt --ei m -1` 뒤 안내 중이 아닌 내비에서 `$R event --es type LOW_ENERGY --es source veh_DEMO3` → `surface: card LOW_ENERGY … tbt=none|unknown`(바로 뜸). 첫 TBT 응답의 원값 `navi tbt 첫 응답 … rawDistance=` 은 단위 확인용으로 붙여 둔다(docs/10 R16).

> **주(급제동 수신 대상, 2026-10-28, docs/10 R18):** 재캡처 완료 — 지금 동작은 `impl_02_after_panel_only_rear_car.png`·`impl_13_leader_gets_no_brake.png`(위 표). 옛 `impl_02`(지금 파일명 `impl_02_before_card_on_leader.png` — 선두 A 에 "앞쪽 시연 차가 급제동" 카드·소식 줄 — A 패널의 상대는 "뒤 2.1 km")와 `impl_11` 의 급제동 카드는 **선두가 급제동 알림을 받은 장면 = 고치기 전 동작**이다. 지금 규칙에서는 급제동한 차보다 **뒤에 있는 차만** 받으므로 선두 A 에는 누구의 급제동도 뜨지 않는다. 급제동 카드·소식 줄 증거를 다시 찍을 때는 **뒤차 B** 에서 `--es action event --es type HARD_BRAKE`(출처 기본값 = 스냅샷의 내 바로 앞 차 → 로그 `forMe=true basis=SNAPSHOT`)로 주입한다. 선두 A 에서 같은 명령은 `demo: event type=HARD_BRAKE source=ahead(기본) — … → 주입 안 함` 경고만 남긴다(카드가 TBT 를 가리는지 자리만 볼 때는 `--es audience me` 로 강제 — 실제 서버는 선두에게 보내지 않는다).

### 1.4 에뮬레이터 음성 — Pleos TTS 로 자동 동작, Supertonic 은 음질 선택 (2026-10-28, docs/10 R19 해결)
앱은 음성 경로를 스스로 고른다(docs/05 §3.5): **Android `TextToSpeech`(한국어 엔진·ko_KR 사용 가능일 때) → Pleos TextToSpeech SDK ON_DEVICE(pleos flavor) → 화면 표시만**.
Pleos AVD 의 시스템 엔진은 Android `TextToSpeech` 에 안 보이므로(R19) 엔진을 따로 깔지 않은 **Pleos AVD(차 A, pleos flavor)는 Pleos TTS 로 소리가 난다**(설정 없음, 앱 키 없음 — 부하 시 요청 → 시작 5~9 s, 위험 이벤트는 패널 소식 줄 빨간 강조가 먼저 뜬다 docs/05 §5.2). 오픈 소스 오프라인 엔진 Supertonic 3 는 **더 자연스러운 음질이 필요할 때의 선택 사항**이다 — 깔고 기본 엔진으로 지정하면 Android TTS 경로로 읽는다. 차 B(fake flavor)는 Pleos SDK 가 없어 Supertonic 이 없으면 **화면 표시만**이다(시연에서 차 B 음성이 필요하면 설치).

|---|---|---|---|---|

Supertonic 설치(선택, 두 대 모두 한 번만 — 에뮬레이터를 지워도 다시):
```
# 1) 내려받기(156 MB, sha256 760fff23dc75d68b9dca0dcd4dc4d0dfeaabf1f2e31ebb4e37af5037c90bc64b)
curl -L -o supertonic3-ko.apk https://huggingface.co/csukuangfj2/sherpa-onnx-apk/resolve/main/tts-engine-new/1.13.8/sherpa-onnx-1.13.8-x86_64-kor-tts-engine-sherpa-onnx-supertonic-3-tts-int8-2026-05-11.apk
```

확인(어느 경로든): 앱 로그 `voice: 경로 = ANDROID_TTS(engine=com.k2fsa.sherpa.onnx.tts.engine) 사유=1순위 준비` 또는 `voice: 경로 = PLEOS_TTS 사유=ANDROID_TTS 불가(초기화 실패 status=-1 (엔진 없음))`, 디버그 `status` 의 `tts=ready ttsPath=…`, 진단 화면 '음성 안내' 카드 맨 윗줄. Supertonic 은 모델 적재가 무거워 PC 부하가 크면 준비까지 20 s 넘게 걸린다(에뮬레이터 RAM 4 GB 기준 여유 1.8 GB 확인) — 그동안 차 A 는 Pleos TTS 로 읽다가(`ttsSelecting=true`) 준비되면 Android TTS 로 올라간다(선택 상한 30 s, 그 뒤에 준비돼도 올라감). 에뮬레이터는 **`-no-audio` 없이** 띄워야 소리가 난다. preflight 표: `Supertonic 엔진`(없으면 WARN)·`앱 음성 경로 = ANDROID_TTS|PLEOS_TTS`(OK) — 화면 표시만이면 FAIL.

증거(2026-10-28, Supertonic 경로): 차 B(fake) 순정 내비 위 패널에 "아빠 차가 휴게소에 도착했…" 소식 줄이 뜨는 순간 `voice: speak WAYPOINT_ARRIVED` → 에뮬레이터 스피커 출력을 에뮬레이터 콘솔 녹화(`adb emu screenrecord start --time-limit 14 <파일>.webm` — 영상 + 소리 vorbis)로 담았다: `docs/images/tts/proof_waypoint_arrived.mp4`(소리 구간 1.6 s, 최대 -30 dB, Vosk 받아쓰기 "아파트 휴게소에 도착했어요").

#### 1.4.1 심사 환경 재현 — 깨끗한 Pleos AVD + release APK 만 (통합 담당)
심사위원 에뮬레이터에는 Supertonic 이 없다. 그 상태에서 release APK 하나만 깔아 "아빠 차가 휴게소에 도착했어요."가 **Pleos TTS 로 소리 나는지** 녹음으로 증명한다(Git Bash, 저장소 루트, `S` = Pleos AVD 시리얼, `JAVA_HOME` = JDK 17 — apksigner 가 쓴다).
```
S=emulator-5556
# 0) 엔진 없는 상태로: 새 Pleos AVD 를 쓰거나 Supertonic 을 지운다(기본 엔진 설정도 지움)
adb -s $S uninstall com.k2fsa.sherpa.onnx.tts.engine
adb -s $S shell settings --user 10 delete secure tts_default_synth
# 1) release APK 만: debug 앱을 지우고(서명이 달라 덮어쓸 수 없다) release 를 설치.
#    T40 전에는 release 가 미서명(app-pleos-release-unsigned.apk)이라 로컬 기본 debug.keystore 로 서명해 깐다(키·산출물은 커밋하지 않는다)
(cd car-app && ./gradlew :app:assemblePleosRelease)
BT="$LOCALAPPDATA/Android/Sdk/build-tools/36.0.0"; OUT=car-app/app/build/outputs/apk/pleos/release
"$BT/zipalign.exe" -p -f 4 $OUT/app-pleos-release-unsigned.apk $OUT/app-pleos-release-aligned.apk
"$BT/apksigner.bat" sign --ks ~/.android/debug.keystore --ks-pass pass:android --key-pass pass:android --out $OUT/app-pleos-release-local.apk $OUT/app-pleos-release-aligned.apk
adb -s $S uninstall app.donghaeng.car
adb -s $S install $OUT/app-pleos-release-local.apk          # T40 이후에는 apk/{팀명}_동행_release.apk
# 2) 앱 실행(진단 화면으로) → 경로 확인(엔진 없음 → PLEOS_TTS)
adb -s $S logcat -c
adb -s $S shell am start -n app.donghaeng.car/.MainActivity --es screen diagnostics
sleep 15; adb -s $S logcat -d -s DongHaeng | grep -E "voice: 경로|Pleos TTS|TTS 초기화"
#    'Pleos TTS 준비 완료' 가 아직 없고 'initialize 응답 늦음 15s — 계속 기다림' / '… 뒤 다시 시도' 만 있으면(부팅 직후 CaaS 콜드 스타트) 30 s 더 기다려 다시 본다
# 3) [예시 안내 듣기] 자리를 화면 덤프로 찾는다(release 에는 디버그 리시버가 없어 탭으로 누른다 — 좌표를 손으로 정하지 않는다).
#    진단 화면 '음성 안내' 카드(위에서 둘째)의 버튼. 비어 있으면 버튼이 보이게 스크롤한 뒤 다시
adb -s $S shell uiautomator dump /sdcard/dh_ui.xml > /dev/null
read X1 Y1 X2 Y2 <<< "$(adb -s $S exec-out cat /sdcard/dh_ui.xml | grep -o 'text="예시 안내 듣기"[^>]*bounds="[^"]*"' | grep -o 'bounds="[^"]*"' | grep -o '[0-9]\+' | tr '\n' ' ')"
X=$(( (X1 + X2) / 2 )); Y=$(( (Y1 + Y2) / 2 )); echo "button center $X,$Y"
# 4) 녹화 시작 → 곧바로 탭. Pleos 경로는 요청 → 시작이 부하 시 5~9 s(+ 문장 약 3 s)라 녹화는 40초(14초면 문장 도중에 끊길 수 있다)
adb -s $S shell date +%T                                    # 녹화 시작 기기 시각(아래 로그 시각과 비교)
adb -s $S emu screenrecord start --time-limit 40 judge_pleos_tts.webm
adb -s $S shell input tap $X $Y
# 5) 지연·시작 로그(기기 시각 포함) — 40초 뒤 녹화가 끝나면
adb -s $S logcat -d -v time -s DongHaeng | grep -E "diag: 예시|voice: speak SAMPLE|Pleos TTS (시작|실패|생략)"
```
기대: ① 앱 시작 후 `TTS 초기화 실패 status=-1 → 다음 경로 (한국어 엔진 없음?)` · `Pleos TTS 준비 완료 (ON_DEVICE, ko_KR, CaaS 4.2.10) …ms` · `voice: 경로 = PLEOS_TTS 사유=ANDROID_TTS 불가(초기화 실패 status=-1 (엔진 없음))` ② 진단 카드 `지금 경로  PLEOS_TTS  Pleos TTS (ON_DEVICE · ko_KR)`, 후보 `ANDROID_TTS 불가 — 초기화 실패 status=-1 (엔진 없음)` / `PLEOS_TTS 준비 — ON_DEVICE ko_KR 준비 (CaaS …)` ③ 탭 뒤 `diag: 예시 안내 듣기 path=PLEOS_TTS` → `voice: speak SAMPLE priority=LOW len=17` → `Pleos TTS 시작 지연=NNNNms`, 카드 '요청→시작 지연'에 같은 값. **`Pleos TTS 시작 지연=` 줄의 시각이 녹화 시작 기기 시각 + 37 s 안**이면 문장(약 3 s)이 녹화에 다 들어갔다 — 아니면 `--time-limit` 을 늘려 다시 찍는다 ④ webm 소리 트랙에 문장이 들린다(받아쓰기에 "휴게소에 도착" 이 나오면 충분 — Pleos ON_DEVICE 는 받아쓰기 오류율이 높다). 결과는 `docs/images/tts/judge_pleos_tts.webm`(+ 진단 카드 캡처)로 남긴다.
소리가 안 나는데 로그는 정상이면: pleos **debug** 빌드의 날것 프로브로 용도(AudioAttributes) 차이를 본다 — `adb -s <s> shell am broadcast -n app.donghaeng.car/.adapter.voice.PleosTtsProbeReceiver --es mode ON_DEVICE`(용도 지정 없음) 와 `… --ez attrs true`(앱과 같은 내비 안내 용도).

**결과(2026-10-28, 통합 담당):** 새로 만든 깨끗한 AVD `Pleos_Clean`(Pleos 시스템 이미지, `-wipe-data`, Supertonic·동행 앱 없음, CaaS 4.2.10)에 로컬 서명 release APK 만 설치 →
`TTS 초기화 실패 status=-1 → 다음 경로` · `Pleos TTS 준비 완료 (ON_DEVICE, ko_KR, CaaS 4.2.10-coral-aosp) 1130ms` · `voice: 경로 = PLEOS_TTS 사유=ANDROID_TTS 불가(초기화 실패 status=-1 (엔진 없음))` →
진단 [예시 안내 듣기] → `voice: speak SAMPLE` · `Pleos TTS 시작 지연=119ms` → 에뮬레이터 스피커 녹음에 소리 1.9 s(최대 -27.5 dB): `docs/images/tts/judge_clean_avd_release_pleos_tts.mp4`(진단 카드 '지금 경로 PLEOS_TTS' 화면 + 소리).
발음: Vosk 소형 받아쓰기 "한번 책을 휴게실 대책이 상"(문자 오류율 약 80%) — Pleos 화자(seoyoon)는 이 인식기와 잘 맞지 않는다(Supertonic 3 은 같은 문장 "…휴게소에 도착했어요" 로 받아쓰임). 사람이 들어 판단할 몫은 영상으로 남긴다.

**위험 이벤트 강조(같은 날, 차 B — Android TTS 경로 평균 1.3 s):** 음성을 끈 채(`voice --ez on false`) 앞차 급제동 주입 → 1.5 s 에는 평소 소식 줄, 3 s 에 `surface: event highlight BLINK tone=DANGER age=3s path=ANDROID_TTS avg=1343ms` → 빨간 강조 + 깜빡임, 소식 줄 10 s 창이 끝나면 `NONE`:

### 4.1 무전(F16) 장면 확인 — `tools/demo/ptt.py` (2026-10-28)
두 차가 같은 그룹이고(장면 3 이후) 순정 내비가 앞에 있을 때 차 A(보내는 차)·차 B(받는 차)로 확인한다. 서버는 무전 API(docs/03 §2.6)가 들어간 빌드여야 한다.
마이크 대신 **녹음 주입**(Windows 한국어 음성으로 만든 WAV — 저장소에 넣지 않는다)과 **답 주입**(판정 직접 또는 WAV → Vosk)을 쓴다 — AVD 는 `hw.audioInput=no` 라 녹음이 무음이기 때문.

```
python tools/demo/ptt.py audio                                         # 테스트 WAV 5개 → tools/demo/out/ptt_audio (Microsoft Heami)
python tools/demo/ptt.py setup --car-a emulator-5556 --car-b emulator-5558 [--model-zip <vosk-model-small-ko-0.22.zip>]
python tools/demo/ptt.py status --car-a emulator-5556 --car-b emulator-5558
python tools/demo/ptt.py run --car-a emulator-5556 --car-b emulator-5558 --shots                   # yes,no,none,resend,press_cancel,countdown
python tools/demo/ptt.py run --car-a emulator-5556 --car-b emulator-5558 --scenarios yes,no --answer-wav   # 모델이 있으면 Vosk 가 WAV 를 인식
python tools/demo/ptt.py run --car-a emulator-5556 --car-b emulator-5558 --scenarios interrupt,persist --shots   # 사용자 결정 2026-10-28(기본 목록 밖)
```
결과: `tools/demo/out/<시각>_ptt/summary.md`(시나리오·확인·OK/MISS/SKIP·관측 줄) + `carA.log`·`carB.log` + (`--shots`) 녹음·확인·보냄(A)·재생(B) 캡처.

| `voice: yield to mic — <종류> priority=… 멈춤, 무전 뒤 다시` | 무전 녹음 직전 넘겨 둔 NORMAL·LOW 안내를 멈추고 녹음 뒤 다시(B013). 급제동·에어백은 그대로 |
| `voice: group changed → 옛 그룹 문장 N 개 버림(그룹 종료 안내는 남김)` | 그룹이 끝나거나 바뀌면 옛 그룹 안내를 버림(B060) |
| `ptt: mic not usable in background (FGS microphone 없음) → 녹음 안 함 — …` | API 30+ 에서 순정 내비가 앞이고 그룹 서비스에 microphone 타입이 없으면 무음 녹음 대신 안내만(B015). 동행 화면을 한 번 열면 붙는다. 주입 녹음(`ptt.py`)은 상관없다 |
| `ptt: recorded end=… dur=…ms bytes=… inject=false silent=true` | 실마이크 입력이 내내 0 — AVD(`hw.audioInput=no`)면 정상, 실기기면 마이크 확인 |
| `ptt: recognizer ANDROID_STT failed reason=stt error=9 (mic-background) permanent=false` | 마이크가 막힌 상태의 error 9 는 이번만 실패(B045, docs/10 R14). 마이크가 열리는 상태의 9 만 `permanent=true` |
| `surface: card danger <종류> gate skipped (voice late path=… avg=…ms)` · `surface: card danger released (no voice in 3s) type=… after=…s` | '카드 + 음성' 모드의 위험 카드 — 음성이 늦을 게 분명하면 TBT 게이트를 건너뛰고, 3 s 안에 음성이 없으면 놓는다(B067) |

**도구(tools/demo)**
- `demo.py` preflight 에 **음성 안내 켜짐** 행(디버그 `status` 의 `voice=`) — 꺼져 있으면 실행 때 리시버로 켜고 다시 확인(dry-run 은 FAIL 로 알리기만). `voice=` 는 지금 앱(음성 엔진 메모리)의 값이다 — 디버그 `voice`·진단 카드의 전환은 앱을 다시 켜면 사라진다(저장은 설정 화면 스위치 몫, 그 저장 호출은 화면(UI) 트랙 반영 뒤).
- `ptt.py` preflight: 그룹 서비스에 microphone 타입이 없으면 WARN 문구가 '녹음하지 않고 안내만'(B015)으로 바뀌었고, `interrupt` 를 고르면 차 B 도 같은 기준으로 본다(차 B 는 실마이크로 녹음한다).
